## 🧩 How I like to build software

### Clean and maintainable code

I value:

* Clear and readable code
* Modular architecture
* Separation of responsibilities
* Reusable components
* Appropriate abstraction
* Composition and inheritance when they actually make sense
* Consistent conventions across a project
* Avoiding unnecessary duplication and complexity
* Refactoring when a solution starts becoming difficult to maintain

My goal isn't to write the cleverest code possible.

It's to write code that **another person, including future me, can understand without performing archaeological research**.

### Continuous learning

Technology moves quickly, so I try to keep my workflow current by regularly exploring:

* New documentation
* APIs and API changes
* Useful libraries
* Framework updates
* Better development tools
* New approaches to architecture and implementation

I don't want to use a technology just because it is popular. I prefer understanding **what it solves, what its trade-offs are, and whether it actually improves the project**.

### Research before implementation

When a project touches an unfamiliar area, I like to investigate it before jumping into code.

That can include:

* Technical limitations
* Documentation and official specifications
* API capabilities
* Licensing
* Terms of service
* Legal or practical constraints
* Alternative approaches and their trade-offs

Sometimes the most important part of a feature is discovering that the obvious implementation is a terrible idea.

## 💭 A few principles

> **Readable code over clever code.**

> **Understand the system before trying to optimize it.**

> **Use the right abstraction, not every abstraction.**

> **Keep the interface and the architecture equally intentional.**
