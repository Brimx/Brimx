## 🧠 About me

I'm a **Systems Engineering student** with experience across different areas of software development.

I've worked with multiple programming languages and environments, from **C++ and Java to Python and C#**, while also exploring **APIs, web development, desktop applications, frameworks, libraries, and interface design**.

I enjoy learning by building things. Many of the projects I work on begin as a simple idea and gradually turn into an opportunity to investigate architecture, APIs, design decisions, usability, or whatever other rabbit hole the project decides to throw at me.

I'm particularly interested in writing software that is **clean, understandable, modular, and maintainable**. I like keeping systems organized through clear boundaries, reusable components, abstractions, conventions, and design systems such as **design tokens**.

I also believe that building software is not only about whether something *can* be implemented. When a project involves unfamiliar technology, external services, data, licensing, or other constraints, I like researching the **technical, practical, and legal considerations** before making decisions.

## 🧩 How I like to build software

### Clean and maintainable code

I value **clear and readable code, modular architecture, separation of responsibilities, reusable components, appropriate abstraction, composition and inheritance when they actually make sense, consistent conventions across a project, avoiding unnecessary duplication and complexity, and refactoring when a solution starts becoming difficult to maintain**.

My goal isn't to write the cleverest code possible.

It's to write code that **another person, including future me, can understand without performing archaeological research**.

### Continuous learning

Technology moves quickly, so I try to keep my workflow current by regularly exploring **new documentation, APIs and API changes, useful libraries, framework updates, better development tools, and new approaches to architecture and implementation**.

I don't want to use a technology just because it is popular. I prefer understanding **what it solves, what its trade-offs are, and whether it actually improves the project**.

### Research before implementation

When a project touches an unfamiliar area, I like to investigate it before jumping into code.

That can include **technical limitations, documentation and official specifications, API capabilities, licensing, terms of service, legal or practical constraints, and alternative approaches and their trade-offs**.

Sometimes the most important part of a feature is discovering that the obvious implementation is a terrible idea.
